35. El equipo y el tablero

Roles, tareas y comunicación

El TP final se hace en grupos de 2 integrantes. Para que el trabajo avance, cada uno sabe qué le toca, para cuándo y cómo avisar si algo se traba. En este TP el grupo se organiza y arma el tablero y el repositorio que va a usar en el TP final.

Los roles del equipo

  • Coordinación

    Arma el tablero y lo mantiene al día: reparte las tareas, pone las fechas y avisa si algo se atrasa. Al final de cada clase, escribe la bitácora.

  • Repositorio

    Crea el repositorio y suma a su compañero. Ayuda con git pull, git push y los conflictos, y mantiene el README al día.

Los dos aportan

El rol se suma al trabajo: los dos hacen tareas del tablero y commits. GitHub y Trello muestran quién hizo cada cosa, y en la defensa cada uno cuenta cuál fue su rol.

Dividir el trabajo en tareas

Una tarea es algo que una persona puede terminar en una o dos clases. Empieza con un verbo y tiene un responsable y una fecha.

  • Así no

    “README” · “La app”: no dicen qué hay que hacer, son muy grandes y no tienen responsable.

  • Así sí

    “Escribir la sección Integrantes del README” · Lucía · 12/11.

Cómo nos comunicamos

  • El grupo de mensajes, para avisos rápidos: “hoy falto”, “ya subí mis cambios”.

  • El tablero, para saber quién hace qué y para cuándo. Las tareas no se reparten por chat: ahí se pierden.

  • Cinco minutos al empezar la clase: cada uno cuenta qué hizo, qué va a hacer y si algo lo traba.

  • La bitácora, para anotar qué hicimos, qué problemas tuvimos y qué decidimos (lámina 37).

35. El equipo y el tablero (sigue)

El tablero en Trello · sigue

Trello es una página para organizar tareas en un tablero. Cada lista es un estado y cada tarjeta, una tarea. Cada integrante se registra con su mail en trello.com (Sign up, registrarse) y todos trabajan en el mismo tablero.

Armar el tablero

  1. 1Arriba, Create (crear) → Create board (crear tablero). De nombre, TP10 · y el nombre del grupo (por ejemplo, TP10 · GRUPO 1) → Create.
  2. 2Add another list (agregar otra lista) A: Pendiente, En curso y Hecho.
  3. 3Add a card (agregar una tarjeta) B: una tarjeta por tarea, con un verbo.
  4. 4Cuando una tarea empieza o termina, arrastrar su tarjeta C a la lista que sigue.

Responsable, fecha y compartir

  1. 1Tocar la tarjeta para abrirla.
  2. 2Members (miembros) E: quién hace la tarea.
  3. 3Dates (fechas) F: tildar Due date (fecha de entrega), elegir el día y Save (guardar).
  4. 4En el tablero, Share (compartir) D: el mail o el usuario de tu compañero y del docente → Share.

Recomendación: en los cinco minutos del comienzo de la clase, abran el tablero: ¿qué está en curso?, ¿qué se atrasó?, ¿quién toma la próxima tarjeta?

Idea clave: cada integrante tiene un rol y sus tareas. En el tablero, cada tarjeta es una tarea con responsable y fecha, y pasa de lista en lista hasta Hecho.

36. El repositorio del equipo

Colaboradores y pull antes del push

Quien tiene el rol Repositorio crea el repositorio del grupo en GitHub, público y con README (TP7), y suma a su compañero como colaborador: así los dos pueden hacer git push. Todo el grupo trabaja en main.

Sumar a los colaboradores

  1. 1En el repositorio, Settings (configuración) A.
  2. 2En Access, Collaborators (colaboradores) B.
  3. 3Add people (agregar personas) C.
  4. 4El usuario del compañero → Add mateodiaz to this repository (agregarlo) D.

Al compañero le llega un mail: View invitation → Accept invitation (aceptar). Después, git clone.

Todos en main: la rutina

  1. Al empezar

    git pull

    Traemos lo que subieron los demás.

  2. Trabajar y guardar

    git add .git commit -m "…"

    Un commit por cambio.

  3. Antes de subir

    git pull --no-edit

    Traemos lo nuevo y Git lo une con lo nuestro.

  4. Subir

    git push

    Los demás lo traen con git pull.

--no-edit: si hay commits nuevos de los dos lados, git pull los une con un commit nuevo (Merge branch 'main'…) y no abre el editor para escribir su mensaje.

Si te olvidás del pull: push rechazado

Lucía subió un commit y Mateo no hizo git pull antes de su push: GitHub lo rechaza (rejected). No se pierde nada.

Conflictos · sigue

Cuando dos cambian la misma línea: conflicto

Con cambios en líneas distintas, Git los une solo. Si dos cambiaron la misma línea, Git no sabe con cuál quedarse: hay un conflicto y nos pregunta. Lucía y Mateo cambiaron el título del README; Lucía subió primero y, después del git pull --no-edit, Mateo vio esto en VS Code:

  1. 1Arriba, lo nuestro: el cambio actual. Abajo, lo que llegó de GitHub: el cambio entrante.
  2. 2Elegir A B o C, o escribir a mano cómo queda y borrar las marcas <<<<<<<, ======= y >>>>>>>. En un VS Code en inglés: Accept Current Change, Accept Incoming Change y Accept Both Changes.
  3. 3Guardar (Ctrl + S); en la terminal, git add ., git commit -m "…" y git push.

Para que haya menos conflictos: git pull seguido, commits chicos y cada uno con sus tareas del tablero.

Idea clave: todos en main, con git pull al empezar y git pull -‌-no-edit antes de cada push. Si dos cambian la misma línea hay un conflicto: elegimos qué queda y hacemos commit.

37. Documentar el proyecto

El README y la bitácora

Documentar es escribir para otros y para nosotros. El README explica el proyecto a alguien que no lo conoce: qué es, cómo se instala y cómo se usa. La bitácora cuenta, clase por clase, qué hicimos, qué problemas tuvimos y qué decidimos. Los dos son archivos Markdown (.md, TP7) del repositorio.

El README del proyecto

Las secciones que pide el TP final

  • Qué es el proyecto, integrantes y roles.
  • Esquema de red.
  • Requisitos e instalación (npm install) y extensiones de VS Code.
  • Cómo ejecutarlo y manual de uso.
  • Una captura de la app funcionando.

Ya armamos todas las secciones. Completamos lo que ya sabemos y el resto queda en “Pendiente.” hasta el TP final: en el ejemplo siguen Instalación, Cómo se usa y Captura.

La bitácora: una entrada por clase

Cómo se escribe

  • Al final de cada clase, con la fecha.
  • Tres partes: qué hicimos, qué problemas tuvimos y qué decidimos.
  • Concreta: “tuvimos un conflicto en el README” sirve; “trabajamos” no dice nada.
  • La escribe quien tiene el rol Coordinación, con lo que cuenta el compañero. Commit y push antes de irse.

Idea clave: el README explica el proyecto a quien no lo conoce; la bitácora cuenta, clase por clase, qué hicimos, qué problemas tuvimos y qué decidimos. Los dos están en el repositorio y se actualizan con commits.
